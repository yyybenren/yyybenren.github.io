软考系统分析师-基础知识-需求工程与结构化分析

摘要：本文梳理上午考试需求工程部分，包括软件需求的定义、需求开发与需求管理两大过程、业务需求与系统需求等分类、PIECES 框架、九种需求获取方法，以及结构化分析中的功能模型、数据模型、行为模型与数据字典。

一、需求工程概述

软件需求是用户对系统在功能、行为、性能、设计约束等方面的期望，是用户解决问题或达到目标所需的条件或能力，是系统或系统部件要满足合同、标准、规范或其他正式规定文档所需具有的条件或能力，以及反映这些条件或能力的文档说明。

需求工程分为两大过程：

  • 需求开发：需求获取 → 需求分析 → 需求定义（需求规格说明书）→ 需求验证
  • 需求管理：需求基线、变更控制、版本控制、需求跟踪、需求状态跟踪，为需求开发提供支持

二、需求分类

分类 说明
业务需求 反映企业或客户对系统高层次的目标要求，通常来自项目投资人、客户、市场营销部门或产品策划部门，用于确定项目视图和范围
用户需求 描述用户的具体目标，或用户要求系统必须能完成的任务，即用户能使用系统来做什么，通常通过用户访谈和问卷调查整理使用场景来建立
系统需求 从系统角度说明软件需求，包括功能需求、非功能需求和设计约束

系统需求的三个组成部分：

  • 功能需求：也称行为需求，规定开发人员必须在系统中实现的软件功能
  • 非功能需求：系统必须具备的属性或品质，又可细分为软件质量属性（可维护性、可靠性、效率等）和其他非功能需求
  • 设计约束：也称限制条件或补充规约，例如必须采用自主知识产权的数据库系统、必须运行在 UNIX 操作系统之下

从客户角度分类：

  • 基本需求：需求明确规定的功能
  • 期望需求：除基本需求外，客户认为理所应当包含在内的其他功能
  • 兴奋需求：客户未要求的其他功能需求，会浪费项目开发时间和成本

PIECES 框架

PIECES 是系统非功能性需求分类的技术：

维度 说明
性能 Performance 描述企业当前的运行效率，分析当前业务的处理速度
信息 Information 描述业务数据的输入、输出以及处理方面存在的各种问题
经济 Economics 从成本和收益角度分析企业当前存在的问题
控制 Control 提高信息系统的安全和控制水平
效率 Efficiency 提高企业人、财、物等的使用效率
服务 Service 提高企业对客户、供应商、合作伙伴、顾客等的服务质量

三、需求获取方法

  1. 用户访谈：1 对 1～3，选择有代表性的用户
  2. 问卷调查：适用于用户多、无法一一访谈的情况
  3. 现场观摩：针对较为复杂的流程和操作
  4. 联合需求计划 JRP：高度组织的群体会议，各方参与，成本较高
  5. 情节串联板：用一系列图片来讲故事
  6. 收集资料：把与系统有关的、对系统开发有益的信息收集起来
  7. 参加业务实践：有效发现问题的本质并寻找解决办法
  8. 阅读历史文档：对收集数据性的信息较为有用
  9. 抽样调查：降低成本

四、需求分析

需求分析是发现、求精、建模、规约的过程，主要是建立系统模型，创建所需数据、信息和控制流以及操作行为的模型，再对模型进行分析，主要有两种方法：结构化分析方法 SA 和面向对象分析方法 OOA。

结构化分析方法 SA

SA 自顶向下、逐步分解，是面向数据的，强调分析对象的数据流，需要建立三类模型和一份字典：

  • 功能模型：数据流图 DFD，包含数据流、加工、数据存储、外部实体
  • 数据模型：实体联系图 E-R，包含实体、联系
  • 行为模型：状态转换图 STD，包含状态（初态、终态）和事件
  • 数据字典：包含数据元素、数据结构、数据流、数据存储、加工逻辑、外部实体

数据流图

数据流图描述数据在系统中如何被传送或变换，以及如何对数据流进行变换，用于功能建模。

元素 说明
数据流 由一组固定成分的数据组成，表示数据的流向，通常有一个合适的名词反映其含义
加工 描述输入数据流到输出数据流之间的变换
数据存储（文件） 表示暂时存储的数据，每个文件都有名字。流向文件的数据流表示写文件，流出的表示读文件
外部实体 存在于软件系统外的人员或组织

数据流图可以分层，从顶层（上下文无关数据流）到 0 层、1 层等。顶层数据流图只含有一个加工处理，表示整个系统，描述系统的输入输出以及与外部实体的数据交互。

数据项是数据流图的组成部分，不在图中显示，但会在题目说明中描述某条数据流的组成元素。

加工的特点：对每一个基本加工必须有一个加工规格说明；规格说明必须描述把输入数据流变换为输出数据流的加工规则；决策表可以用来表示加工规格说明。

四大模块：传入模块（从下属模块取得数据经处理传送给上级模块）、传出模块（从上级模块取得数据经处理传送给下属模块）、变换模块（从上级模块取得数据进行特定处理，转换成其他形式再送回上级模块）、协调模块（对所有下属模块进行协调和管理）。

数据字典

数据字典用来定义数据流图中出现的符号或名称的含义，图中每个存储、加工、实体的含义都必须定义，并且父图与子图之间这些名称要相同。

符号 含义 举例
= 被定义为 x = a + b，表示 x 由 a 和 b 组成
+ 与 ——
[ , ] 或 [ | ] 或 x = [a, b]，表示 x 由 a 或由 b 组成
{ } 重复 x = {a}，表示 x 由 0 个或多个 a 组成
( ) 可选 x = (a)，表示 a 在 x 中可出现也可不出现

数据流图的设计原则

  1. 数据守恒原则：对任何一个加工，其所有输出数据流中的数据必须能从该加工的输入数据流中直接获得，或通过该加工产生
  2. 守恒加工原则：对同一个加工，输入与输出的名字必须不相同，即使组成成分相同
  3. 每个加工必须既有输入数据流又有输出数据流
  4. 外部实体与外部实体之间不存在数据流
  5. 外部实体与数据存储之间不存在数据流
  6. 数据存储与数据存储之间不存在数据流
  7. 父图与子图的平衡原则：子图的输入输出数据流同父图相应加工的输入输出数据流必须一致，此原则不存在于单张图
  8. 数据流与加工有关，且必须经过加工

常见异常现象：黑洞（加工只有输入数据流没有输出数据流）、奇迹（加工只有输出数据流没有输入数据流）、灰洞（加工的输入数据流无法通过加工产生输出流）。

状态转换图

状态转换图属于行为模型，用于描述系统在不同事件影响下的状态变化，通过展示系统的各种状态以及导致状态变化的事件来表达系统的行为模式。

五、需求变更与需求跟踪

需求变更和风险

需求变更过程中需要关注需求风险管理，带有风险的做法有：无足够用户参与、忽略了用户分类、用户需求不断增加、模棱两可的需求、不必要的特性、过于精简的 SRS、不准确的估算。

变更产生的原因：外部环境的变化、需求和设计做得不够完整、新技术的出现、公司机构重组造成业务流程的变化。

变更控制委员会 CCB 也称配置控制委员会，其任务是对建议的配置项变更做出评价、审批，以及监督已经批准变更的实施。

需求跟踪

需求跟踪是双向跟踪，分为两个层次：正向跟踪表示用户的原始需求是否都实现了，反向跟踪表示软件实现的是否都是用户要求的，不多不少。可以用原始需求与用例的对照表（需求跟踪矩阵）来表示：

  • 若原始需求与用例有对应，则在对应栏打勾
  • 若某一行都没有勾，表明该原始需求未实现，正向跟踪发现问题
  • 若某一列都没有勾，表明有冗余功能用例，软件实现了多余功能，反向跟踪发现问题
